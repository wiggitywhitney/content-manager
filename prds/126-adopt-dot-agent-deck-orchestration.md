# PRD: Adopt dot-agent-deck orchestration

**Issue**: [#126](https://github.com/wiggitywhitney/content-manager/issues/126)
**Status**: Not Started
**Priority**: High
**Created**: 2026-09-11

## Problem Statement

Work on this repo currently runs in a single Claude Code session end to end — the same agent implements, tests, and reviews its own changes. A reviewer that shares the author's model shares the author's blind spots; there is no structural check that catches what the implementing agent itself would miss.

## Solution Overview

Install [`dot-agent-deck`](https://github.com/vfarcic/dot-agent-deck) (Viktor Farcic's terminal dashboard + daemon that runs several agent CLI sessions as panes and passes messages between them) and configure it for this repo, following his own actual usage rather than the tool's own dogfooding demo.

**Context that grounded Milestone 0's design decisions**, established during prior research and resolved into Decisions #6-10 below:

- `dot-agent-deck`'s own `.dot-agent-deck.toml` (its dogfooding config) defines three orchestration presets — `mixed`, `anthropic`, `GPT` — each with six roles (orchestrator, coder, reviewer, auditor, tester, release). Only the `mixed` preset actually splits vendors across roles (reviewer on `pi`, auditor on `opencode`, the rest on Claude).
- **`dot-ai`** (a real project Viktor runs it on) uses a single orchestration with **seven** roles: the same six plus a `documenter` role. Orchestrator, coder, reviewer, auditor, and documenter all run the *same* command (`devbox run agent` — one Claude harness). Only `tester` and `release` differ, and both differences are Claude-side configuration, not a different vendor. **No cross-vendor mixing is actually running in this config.**
- **`dot-ai-infra`** doesn't use the orchestration/roles feature at all — just a monitoring mode with status panes.
- Conclusion carried into this PRD, and confirmed by Milestone 0: the mixed-vendor idea is real and demonstrated, but it is not what Viktor's own production usage runs — this repo adopts the `dot-ai` pattern (same-vendor Claude, `documenter` role, no cross-vendor split) per Decisions #6 and #7.

## User Experience

### Current workflow
1. Whitney works PRDs in a single Claude Code session using the existing `/prd-*` skills.
2. The same session implements, tests, and reviews its own work; CodeRabbit is the only outside check, and it runs post-hoc against a pushed branch.

### New workflow (after this PRD)
1. Whitney opens `dot-agent-deck`'s TUI and hands the orchestrator a PRD to work.
2. The orchestrator reads the PRD, produces a test-plan table, and stops for Whitney's sign-off (Gate 1).
3. Separate agent roles handle implementation, testing, review, and audit, running unattended between the two gates.
4. Whitney reviews and confirms before merge (Gate 2).

## Technical Architecture

- **Tool**: `dot-agent-deck`, installed via `brew tap vfarcic/tap && brew install dot-agent-deck` (Decision #1 — not the bare `brew install dot-agent-deck` originally assumed). Infrastructure (a Rust daemon + TUI), not a prompt or skill — it owns process lifecycle, message delivery, and idle detection.
- **Config location**: `.dot-agent-deck.toml` at this repo's root, per-project — matching how Viktor's own `dot-ai` and `dot-ai-infra` each carry their own config rather than a shared central one.
- **Config authoring**: start from `dot-agent-deck`'s own project-analyzing generator (`Ctrl+d` then `g` in the dashboard) or `dot-agent-deck init`'s starter template, then tune against `dot-ai`'s pattern (Decision #2) — not a hand-authored config copied wholesale from `dot-ai`.
- **Devbox scripts**: each role invokes `devbox run <script>` (e.g. `agent-coder`, `agent-tester`); this repo has no `devbox.json` today, so the scripts need to be defined from scratch, not copied from an existing setup. Every such role must also set an explicit `agent = "claude"` key on its block (Decision #3) — without it, the deck cannot tell what a launcher command runs and the role gets no status tracking.
- **Escalation model**: two user gates only — test-plan approval before delegation begins, and merge confirmation at the end. Everything between runs unattended.
- **Idle-worker timeout**: if `worker_response_timeout_minutes` is customized, it must be a top-level key positioned above every `[[modes]]`/`[[orchestrations]]` table header in the file, or it is silently absorbed into the last table and does nothing (Decision #4).
- **Notification channel**: Viktor's own config notifies via Telegram at four moments (escalation, merge gate, run finished, worker-stuck), but this is an unshipped example recipe, not a deck feature — the channel is arbitrary (Slack MCP, `ntfy`, desktop notifier, SMS, webhook all work identically) and carries real security requirements regardless of choice (Decision #5). This repo replaces Telegram with Slack via incoming webhook (Decision #9).

## Success Criteria

- `dot-agent-deck` is installed and its daemon/TUI runs against this repo without error.
- A `.dot-agent-deck.toml` exists at the repo root defining every role decided in Milestone 0, each backed by a working devbox script.
- The orchestrator's prompt correctly reads this repo's `prds/[id]-*.md` files and produces a test-plan table Whitney can approve.
- PRD #125 (auto-adjusting posting cadence) is successfully implemented end to end through the deck, validated entirely via the existing test suite, from test-plan approval through merge confirmation, with the `release` and `documenter` roles' handoffs also verified — this run doubles as the deck's own validation (Decision #10).
- The two-gate model holds in practice: no role blocks on or requires a response from Whitney outside the test-plan (`escalation`) and merge (`merge-gate`) gates — the `run-finished` and `worker-stuck` Slack pings (Decision #9) are non-blocking informational notices and don't count as a third gate.
- No role directly invokes `sync-content.js`, `scan-new-content.js`, `post-social-content.js`, or `update-page-visibility.js` against production credentials or the live spreadsheets during PRD #125's run through the deck.
- The webhook URL used for Slack notifications never appears in `.dot-agent-deck.toml`, any role's prompt text, or logs — verified by inspecting the committed config and a sample run's logs.

## Decision Log

*(Populated as Milestone 0 and later milestones make real decisions. Decisions #1-10 below resolve the prior research in the Context subsection under Solution Overview above into final decisions.)*

### 1. Installation command and hook setup
**Decision**: Install via `brew tap vfarcic/tap && brew install dot-agent-deck`, not the bare `brew install dot-agent-deck` originally assumed. **Confirmed by Decision #12's live check (v0.41.0, installed in this repo)**: no separate `hooks install` step is needed — agent-detection hooks are auto-installed on every dashboard startup for whichever agents are detected (Claude Code, OpenCode, Codex, Devin), idempotently and best-effort. `dot-agent-deck hooks install`/`hooks uninstall` exist only as manual troubleshooting commands (repair a broken hook pointing at a stale build path, temporarily remove hooks, re-record Codex trust) — not a required setup step. The command takes no positional argument, only `--agent <AGENT>` (default `claude-code`).
**Rationale**: Verified directly against the actually-installed tool (`dot-agent-deck --help`, `dot-agent-deck hooks install --help`) and the current `docs/getting-started.md`/`docs/troubleshooting.md` fetched from `vfarcic/dot-agent-deck` at v0.41.0, resolving Decision #12's four conflicting claims: (a) this decision's original auto-install claim and (d) the second CodeRabbit review's "auto at startup, manual is optional" framing are both confirmed correct; (b) the research pass's "hooks install is a required separate step" is contradicted; (c) the first CodeRabbit review's syntax claim (no positional arg, `--agent` for non-Claude integrations) is confirmed correct by the CLI's own `--help` output. The bare install command would still fail outright since the tool isn't in Homebrew's default tap — that half was never in question.

### 2. Config authored via the tool's own generator, not hand-copied from `dot-ai`
**Decision**: Milestone 0 and the `.dot-agent-deck.toml` milestone start from `dot-agent-deck`'s own project-analyzing generator (`Ctrl+d` then `g` in the dashboard) or `dot-agent-deck init`'s starter template, then tune the result against `dot-ai`'s pattern — rather than hand-authoring a config copied wholesale from `dot-ai` as originally planned.
**Rationale**: This is Viktor's own documented recommended path (`docs/getting-started.md`: "The fastest way to get the config is to let an agent generate it... Treat the result as a starting point and tune it as you learn what works for your project"). A project-specific proposal is more likely to fit this repo's actual structure than porting a different project's config verbatim.

### 3. `agent` key required for every launcher-wrapped role
**Decision**: Every role in `.dot-agent-deck.toml` that invokes its harness through a `devbox run <script>` launcher must also set an explicit `agent = "claude"` (or the appropriate value) on that role's block.
**Rationale**: The deck identifies an agent by reading the first word of a pane's command; a launcher like `devbox run agent-coder` hides that. Without the explicit `agent` key the role gets **no status tracking at all** (confirmed in `docs/configuration.md`). This was missing from the original plan and would have silently broken dashboard visibility for every role.

### 4. `worker_response_timeout_minutes` placement
**Decision**: If a custom idle-worker timeout is set, `worker_response_timeout_minutes` must be written as a top-level key positioned above every `[[modes]]`/`[[orchestrations]]` table header in `.dot-agent-deck.toml`.
**Rationale**: TOML assigns any key written after a table header to that table; a misplaced timeout is silently absorbed into the last table, `dot-agent-deck validate` still reports the config valid, and the daemon quietly keeps the 120-minute default with no error anywhere (confirmed in `docs/idle-workers-and-notifications.md`). This resolves the open question about stuck-worker behavior: the mechanism already exists in the tool and needs no new convention here, only correct placement.

### 5. Notification design: idle-worker detection and the notification recipe are separate; channel choice carries real security requirements
**Decision**: Treat idle-worker detection (the `worker_response_timeout_minutes` daemon timer) as a real, tested feature to configure, separate from the four-moment "notify a human" recipe, which is unshipped example prompt text from Viktor's own project, not a deck feature. If the notification recipe is adopted, whatever channel replaces Telegram (Slack MCP, `ntfy`, desktop notifier, SMS, webhook — the deck has no opinion) must: always pass an explicit destination id from configuration rather than falling back to "most recently active," never let the agent read the channel's inbound/updates side, and pin the MCP server's version rather than tracking `@latest`. Only the orchestrator ever notifies; workers never do.
**Rationale**: Sourced from `docs/idle-workers-and-notifications.md`. The security requirements are stated as requirements, not suggestions, for this class of setup — an unauthenticated inbound channel is a prompt-injection path, and omitting an explicit destination id lets anyone who discovers the bot's identity intercept the next notification. Also worth weighing: notification instructions living in the orchestrator's prompt can be silently lost on context compaction, while the daemon's idle-worker report cannot, since it's injected fresh at fire time.

### 6. Role set: `dot-ai`'s seven roles
**Decision**: Adopt `dot-ai`'s seven roles — orchestrator, coder, reviewer, auditor, tester, release, documenter — rather than the base six from `dot-agent-deck`'s own dogfooding presets.
**Rationale**: Matches Viktor's actual production usage on `dot-ai`, and this repo's own PRD workflow already treats documentation as a required closing step (`docs/dot-agent-deck.md`, `PROGRESS.md`, `ROADMAP.md`) — a dedicated `documenter` role fits that existing pattern rather than folding it into `coder` or `orchestrator`.

### 7. Vendor/harness: same-vendor Claude throughout
**Decision**: All seven roles run on Claude, matching `dot-ai`'s actual usage — not the mixed-vendor split (`pi` for reviewer, `opencode` for auditor) from `dot-agent-deck`'s own `mixed` dogfooding preset.
**Rationale**: Avoids installing and maintaining two additional agent CLIs for a split that isn't what Viktor's own production project actually runs. Trade-off accepted explicitly: this does not give a structurally different model as reviewer/auditor, only a separate Claude session with separate context — a real but weaker form of independence than mixed-vendor review would give against this PRD's stated problem (a reviewer sharing the author's blind spots).
**Addendum (does not contradict this decision)**: "Same-vendor" governs the harness (Claude Code CLI for every role), not the specific model tier within it. Decision #14 pins `release` to `claude --model sonnet` while every other role uses the default model — this is a per-role model-tier choice within the single-vendor Claude harness this decision already established, not a departure from it.

### 8. Devbox script naming: one script per role
**Decision**: Each role gets its own `devbox run` script named `agent-<role>` — `agent-orchestrator`, `agent-coder`, `agent-reviewer`, `agent-auditor`, `agent-tester`, `agent-release`, `agent-documenter` — rather than one shared script taking a `--role` argument.
**Rationale**: Matches `dot-ai`'s own naming convention (`agent-coder`, `agent-tester`) that its config already references, and keeps each role's `agent = "claude"` key (Decision #3) attached to an unambiguous, individually-editable script block.

### 9. Notification channel: Slack via incoming webhook, delivered through a fixed wrapper script — never through the agent prompt
**Decision**: Replace Viktor's Telegram notifications with Slack, delivered via a single incoming webhook URL stored as a GSM secret — not a Slack bot token + `chat.postMessage`, and not an MCP server. The webhook URL is read only by a small fixed notifier script (e.g. `scripts/notify-slack.sh`) that this repo owns; it accepts nothing but one of four kebab-case event identifiers as its single argument — `escalation`, `merge-gate`, `run-finished`, `worker-stuck` (not the space-containing names used in prose elsewhere in this PRD) — and does the `curl` itself. The orchestrator's prompt tells it *when* to call the script and with which event identifier — it never sees, holds, or is told the webhook URL itself, so the URL cannot appear in `.dot-agent-deck.toml`, in prompt text, in the orchestrator's own output, or in logs. This guarantee is scoped to those three surfaces (config, prompt/model context, logs) — the actual threat this decision defends against (a malicious/malformed PRD tricking the orchestrator into leaking a secret it holds). It is not a claim that no other same-machine process could ever observe the URL by other means (e.g. inspecting `/proc` for another process's environment, or shell tracing) — that would require the OS-level process isolation already declined above as disproportionate for this repo's single-operator setup. The script enforces a 5-second connect timeout and 10-second total timeout, treats any non-2xx response or timeout as a failed send (logged, not raised as an error), and **always exits 0 regardless of send outcome** — a failed notification is recorded but must never stop the orchestrator's shell invocation or trip a `set -e` path, and does not retry. Of the four events, only `escalation` and `merge-gate` are the two user-facing gates in the Success Criteria's "two-gate model"; `run-finished` and `worker-stuck` are informational pings that don't block Whitney or require her response, so they don't violate that criterion (see the Success Criteria wording below). Before wiring the script into the orchestrator's config, send one manual test invocation to a real Slack channel to confirm delivery — no mocked-endpoint test is needed for a single fire-and-forget call with a response that isn't otherwise parsed.
**Rationale**: An incoming webhook is bound to one specific channel at creation time, satisfying Decision #5's "explicit destination id" requirement by construction. It is push-only with no inbound/updates side to read, satisfying the "never let the agent read the channel's inbound side" requirement without extra care. And because there's no MCP server involved at all, the "pin the MCP server's version" requirement doesn't apply. CodeRabbit correctly flagged that putting the webhook URL in the orchestrator's own config or prompt is a prompt-injection risk regardless of GSM storage: GSM only protects the secret at rest, not once it has entered model context, and the orchestrator's job is to read PRD files — untrusted-ish input a malicious or malformed PRD could exploit to get the model to leak the URL. A fixed wrapper script that takes only an event identifier closes that path entirely. A later CodeRabbit round added three more findings, all addressed above: (1) the event names as originally written contain spaces, which breaks an unquoted shell call — switched to kebab-case identifiers; (2) the script's exit-status contract was unspecified, so a non-zero exit on failure could itself stop the orchestrator even though "don't block the run" was already the stated intent — fixed by requiring exit 0 unconditionally; (3) requiring `run-finished`/`worker-stuck` notifications while also stating "no role notifies... outside the test-plan and merge gates" (Success Criteria) was a real contradiction — resolved by clarifying that only `escalation`/`merge-gate` are the two blocking gates, and the other two are non-blocking informational pings.

**Scope pushback (recorded, not actioned)**: A still-later round noted that `scripts/notify-slack.sh` lives inside the git checkout the coder/tester/reviewer/auditor roles can edit, so a malicious or compromised PRD could in principle direct a role to tamper with the script itself and exfiltrate the webhook URL — potentially before that tampering ever shows up in a merge-gate diff review, since the orchestrator could invoke the modified script mid-run. This is real but declined as disproportionate, for the same reason as the OS-process-isolation finding above: a leaked Slack incoming webhook's blast radius is posting messages into one channel — no account takeover, no access to any other system, and it's trivially rotated in the Slack admin UI. Building tamper-resistance (an immutable helper stored outside the checkout, itself of limited value against a role with general filesystem write access anyway) is not proportionate to that risk for this single-operator repo. If a higher-value secret is ever routed through a similar fixed-wrapper pattern in the future, this tradeoff should be revisited.

### 10. Dry-run scope: run PRD #125 directly, but no role runs the live scripts against production
**Decision**: Skip naming a separate low-stakes task for the dry-run milestone. Run PRD #125 (auto-adjusting posting cadence) directly through the deck as the first real run — validated entirely through the existing test suite: `npm test`, `npm run test:e2e` (which already control their own fixtures/dry-run state), and `npm run check-secrets` (this repo's configured acceptance gate per `.claude/verify.json`). No role invokes `sync-content.js`, `scan-new-content.js`, `post-social-content.js`, or `update-page-visibility.js` directly against production credentials or the live spreadsheets during this run, under any circumstance, including as a manual spot-check — there is no exception to this rule. (An earlier draft of this decision carved out a "manual check" exception with per-script dry-run flags; that carve-out is removed, since it undermined the "never" it was attached to — a role could follow the exception's own instructions and still violate the rule, per a CodeRabbit finding.) Whitney reviews the run's output at the merge gate and decides separately, as an explicit follow-up action outside this PRD's automated run, whether and when to actually exercise the pipeline live. If the deck's config, prompts, or role handoffs turn out broken before reaching the merge gate, discard that branch without merging and fix the config — rather than spending a milestone validating on throwaway work first.
**Rationale**: Whitney's call, refined across three rounds of CodeRabbit findings. The first round flagged that `daily-sync.yml` forces `DRY_RUN=false` for the sync step and `post-social-content.js`'s workflow invocation doesn't set `DRY_RUN` at all. The second round went further: `DRY_RUN=true` isn't sufficient on its own, because (a) `scan-new-content.js` doesn't read the `DRY_RUN` env var at all — verified in `src/scan-new-content.js`, it only checks `args.includes("--dry-run")` — so an env-only guard would silently fail to prevent a real spreadsheet write from that script, and (b) `update-page-visibility.js` was verified to have no dry-run support of any kind — grepping the file finds no `DRY_RUN` or `dry-run` reference at all. A third round caught that the "manual check" exception (a still-earlier draft of the decision text above) reintroduced the exact risk the rule existed to close, since it permitted direct invocation with a per-script flag instead of ruling it out entirely — removed accordingly. Given all that, the safer and simpler rule is that PRD #125's validation run doesn't invoke any of these production scripts directly in the first place, with no exception — the existing test suite is what's meant to exercise this code path safely, and this repo's PRD workflow already runs it as a matter of course. This merges the "Dry run validated on a low-stakes task" milestone into "PRD #125 implemented through the deck" below — see the updated Milestones section.

**Scope pushback (recorded, not actioned)**: The same review round that caught the manual-check contradiction also (a) disputed deferring the `test:e2e` production-scoped-credential gap to [issue #127](https://github.com/wiggitywhitney/content-manager/issues/127), arguing this PRD's validation run still depends on that unsafe credential even without direct script invocation, and (b) asked for a separate OS-level identity/process isolation boundary between the Slack notifier script and the agent roles, so an agent process couldn't read the notifier's GSM credential or observe its `curl` invocation. Both are declined for this PRD, with rationale recorded here rather than silently dropped: (a) issue #127 was already deliberately opened as a separate, out-of-scope tracked item with Whitney's explicit sign-off in the previous round; a reviewer re-raising the same concern isn't new information that changes that call, and re-litigating it every round would make this PRD's design phase open-ended. If `test:e2e`'s credential scope turns out to matter in practice once PRD #125 actually runs through the deck, that's what issue #127 is for. (b) Separate OS-level service identities for the notifier vs. agent processes is real infrastructure to build and operate, aimed at a threat model — an adversarial process on the same host attempting to read another process's credential — that doesn't match this repo's actual environment: this is a single-operator tool where Whitney is the only person running every process (agent roles and the notifier alike) under her own account on her own machine, using the same `vals exec` secret-injection pattern already used throughout this repo. The webhook-URL-out-of-prompt/config/logs protection in Decision #9 remains real and worthwhile against its actual threat (a malicious/malformed PRD tricking the orchestrator into leaking a secret it holds); OS-level process separation defends against a different, here-inapplicable threat, and building it would be disproportionate effort for this PRD's actual risk profile.

### 11. devbox install method corrected: no Homebrew tap exists — curl script only
**Decision**: Install `devbox` via `curl -fsSL https://get.jetify.com/devbox | bash`, not via Homebrew. The "`dot-agent-deck` and devbox installed" milestone's original text ("Install via `brew tap vfarcic/tap && brew install dot-agent-deck` ... and devbox") incorrectly implied Homebrew also installs devbox — it does not, and no brew tap for devbox exists under any org name (neither the assumed `jetpack-io/devbox/devbox` nor `jetify-com/devbox/devbox`). Devbox auto-installs Nix itself on first `devbox shell`/`devbox run` if Nix isn't already present — no separate Nix install step is needed either.
**Rationale**: [Research: devbox install and scripts](../docs/research/devbox-install-and-scripts.md), verified against `jetify-com/devbox`'s own README and docs. An open GitHub feature request asking for brew support (`jetify-com/devbox` issue #76, filed 2022) is still unresolved, confirming this isn't a renamed/relocated tap but the absence of one entirely. Separately, the same research confirmed devbox is not a `dot-agent-deck` dependency at all — it appears in that tool's own docs only as an example wrapper pattern and as the contributor toolchain for `dot-agent-deck` itself. Wrapping this repo's `agent-<role>` scripts in `devbox run` remains this PRD's own choice (Decision #8), independent of anything `dot-agent-deck` requires — this doesn't change Decision #8, it just confirms devbox's install path needed its own correction rather than riding along with `dot-agent-deck`'s brew install.

### 13. `devbox.json` `packages` field left empty
**Decision**: No packages are declared in `devbox.json`. **Rationale**: Obvious call, resolved without consultation per Whitney's instruction to proceed on decisions with no genuine trade-off. Every `agent-<role>` script only invokes the already-installed `claude` CLI; there is nothing for a declared package to provide.

### 14. Devbox script command bodies verified against `dot-ai`'s actual config
**Decision**: `agent-orchestrator`, `agent-coder`, `agent-reviewer`, `agent-auditor`, `agent-documenter`, and `agent-tester` each run bare `claude`. `agent-release` runs `claude --model sonnet`.
**Rationale**: [Research: dot-ai devbox config verification](../docs/research/dot-ai-devbox-config-verification.md) fetched Viktor Farcic's actual `dot-ai` repo rather than inventing command bodies from scratch, per Whitney's instruction to check his reference implementation before asking her to weigh a trade-off he's already resolved in practice. His real `devbox.json` scripts are `"agent": ["claude"]`, `"agent-tester": ["claude"]`, and `"agent-medium": ["claude --model sonnet"]`; his `.dot-agent-deck.toml` maps orchestrator/coder/reviewer/auditor/documenter/tester to the plain-`claude` scripts and only `release` to the sonnet-pinned one. Whitney confirmed matching this exactly when asked directly (genuine trade-off: sonnet's cost/mechanical-work fit for release's job — merge confirmation, tagging, changelog — versus the simplicity of one uniform command across all seven roles; she chose to match dot-ai's sonnet pin). See Decision #7's addendum: this is a per-role model-tier choice within the single-vendor Claude harness, not a departure from same-vendor Claude.

### 15. Permission handling for unattended roles: `--dangerously-skip-permissions` paired with Claude Code's `/sandbox` feature
**Decision**: Every `agent-<role>` script invokes `claude` with `--dangerously-skip-permissions`, and all three of `sandbox.enabled: true`, `sandbox.failIfUnavailable: true`, and `sandbox.allowUnsandboxedCommands: false`, so the OS-enforced `/sandbox` feature is active, hard-required on failure, and cannot be bypassed via its documented unsandboxed-retry escape hatch, for every unattended role. **Scope correction (see Decision #17's revision below): this containment applies only to Bash/PowerShell/Monitor commands and their children — Read, Edit, Write, WebFetch, and MCP tool calls are governed by the separate permission system, not the sandbox, and become fully unrestricted once `--dangerously-skip-permissions` is set, regardless of sandbox settings.** This residual gap is real, not a rounding error: a role using the Write tool directly (not via a Bash command) to create or overwrite a file is not contained by anything in this decision.
**Rationale**: A genuine three-way trade-off, resolved by research rather than left to guesswork. Two earlier options were considered: (a) blanket `--dangerously-skip-permissions` alone — simple, but gives every role, including reviewer and auditor, unrestricted file/bash/git access with zero containment, undermining the Success Criteria's "no role touches production scripts" commitment by relying on role behavior rather than a structural limit; (b) a scoped per-role tool allowlist matching this repo's existing `.claude/settings.local.json` convention — Whitney reported this doesn't work reliably in practice, still producing frequent permission prompts even when configured. [Research: devbox and Claude Code sandboxing](../docs/research/devbox-and-claude-code-sandboxing.md) confirmed why: Claude Code's own docs describe permission-allowlist matching as "best-effort, not a hardened shell sandbox," with documented gaps (subshells, piped/chained commands, exec wrappers like `find -exec`) that cause prompts to fire despite a matching allow rule. The same research confirmed devbox itself provides zero OS-level sandboxing (Nix package isolation only — a devbox-launched process has full, ordinary host filesystem and network access) — so devbox provides no help here either. Separately, Claude Code has a real, named, OS-enforced `/sandbox` feature (Seatbelt on macOS, bubblewrap+socat on Linux/WSL2) that restricts what a Bash/PowerShell/Monitor command and its children can reach at the OS level, orthogonal to and more reliable than the permission-prompt system. Pairing skip-permissions with `/sandbox` meaningfully reduces the exposure of option (a) — Bash-executed actions are now contained — without reintroducing option (b)'s prompt-friction problem. This dominated both earlier options once the research landed, so it was resolved without a further pause, per Whitney's instruction to proceed on decisions with no remaining genuine trade-off. **A CodeRabbit review of this same decision caught two further issues, both verified against the sandboxing docs before acceptance rather than taken on the reviewer's say-so.** First, all three settings are required together, not `failIfUnavailable` alone: `sandbox.enabled: true` is required because the sandbox is opt-in and off by default even per-project; `sandbox.failIfUnavailable: true` is required because the sandbox fails open (silently runs unsandboxed) by default if it can't start; and `sandbox.allowUnsandboxedCommands: false` is required because the sandbox docs describe a documented "escape hatch" (`dangerouslyDisableSandbox`) that, unless explicitly disabled, lets any command the sandbox blocks simply retry unsandboxed — silently reproducing the unprotected blanket-skip scenario option (a) was rejected for. Any one of the three omitted leaves a real gap, not a redundancy. Second, the review correctly flagged that the sandbox's containment doesn't extend past Bash/PowerShell/Monitor — confirmed directly against the docs ("It applies only to Bash, PowerShell, and Monitor commands and their child processes"; "in-process tools such as WebFetch still follow their permission rules") — which is the scope correction stated above. This decision therefore no longer claims to solve the full containment problem, only the Bash-executed-actions slice of it; whether the remaining gap (Edit/Write/WebFetch/MCP) is accepted or needs further mitigation is Whitney's call, not resolved here.

### 16. Declined: devcontainer/VM layer on top of the sandbox
**Decision**: Not adopting a devcontainer or VM as an additional defense-in-depth layer around the sandboxed `claude` sessions, despite this being Anthropic's own recommended pattern for fully unattended operation.
**Rationale**: Same reasoning as Decision #9's already-established precedent, which declined a separate OS-level process-identity boundary between the Slack notifier script and the agent roles: this is a single-operator repo where Whitney is the only person running every process under her own account on her own machine. Building and maintaining a devcontainer/VM layer is disproportionate effort for that threat model, on top of the real containment Decision #15's `/sandbox` requirement already provides. Precedent-based call, not a new trade-off requiring consultation.

### 17. Revised: the three `sandbox.*` settings go inline on each `agent-<role>` script via `--settings`, not in a repo-root `.claude/settings.json`
**Decision (supersedes this decision's original text)**: Each `agent-<role>` devbox script's `claude` invocation carries the three settings inline via the CLI's per-invocation override — `claude --dangerously-skip-permissions --settings '{"sandbox": {"enabled": true, "failIfUnavailable": true, "allowUnsandboxedCommands": false}}'` — rather than a repo-root committed `.claude/settings.json`.
**Rationale**: The original version of this decision (create a new committed `.claude/settings.json`) was reasoned from only one goal — reconstructability from git history — without checking whether repo-root settings apply narrowly to the deck's launched sessions or broadly to every `claude` invocation in the repo. A CodeRabbit review caught this gap, and it was verified rather than accepted outright: [Research: devbox and Claude Code sandboxing](../docs/research/devbox-and-claude-code-sandboxing.md) confirmed a repo-root `.claude/settings.json`'s sandbox settings apply to **every** session opened in that repo, including Whitney's own normal interactive terminal use — there is no built-in "only unattended/automated invocations" scoping. Forcing `sandbox.enabled`/`failIfUnavailable`/`allowUnsandboxedCommands` onto her everyday interactive work in this repo was never the intent and was never surfaced as a choice in the original decision. The documented per-invocation override (`claude --settings '{...}'`, confirmed in the same research) scopes the setting to exactly one launch. Using it inline in each `agent-<role>` script's command body — which is itself part of the committed `devbox.json` — satisfies the original reconstructability goal just as well as a separate settings file would, while avoiding the unintended scope creep entirely. This dominates the original approach once the gap was found, so it's resolved without a further pause.

### 18. Accepted: the sandbox's Edit/Write/WebFetch/MCP gap is not further mitigated
**Decision**: Accept that `--dangerously-skip-permissions` paired with the sandbox (Decision #15) contains Bash/PowerShell/Monitor-executed actions only. A role using the Write tool directly (not via a Bash command) to create or overwrite a file, or the WebFetch/MCP tools to reach arbitrary network endpoints, is not restricted by anything in this setup. No further mitigation (e.g., a non-blanket permission mode limiting Edit/Write to the working directory) is being investigated for this PRD.
**Rationale**: Whitney's call, consistent with this PRD's established precedent (Decision #16's declined devcontainer/VM layer, Decision #9's declined OS-level process isolation): both already accepted the same shape of risk — a malicious or malformed PRD manipulating an agent role — as disproportionate to engineer around for a single-operator machine where Whitney is the only person running every process under her own account, with the merge-gate review catching resulting damage in the diff before it reaches main. Noted explicitly: unlike Decision #16 (declining an extra layer on top of real containment that already exists for Bash), this decision declines the only containment mechanism for file-write/network actions taken directly through a tool rather than through Bash — there is no partial mitigation already in place for this specific surface, making this a starker acceptance than Decision #16's. Recorded as a distinct decision rather than folded into #15 or #16 so a future reader sees this gap was surfaced, considered, and knowingly accepted — not overlooked.
